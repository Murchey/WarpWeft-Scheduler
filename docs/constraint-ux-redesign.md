## 0. 决策摘要

1. **不把求解器参数直接暴露给用户。** 默认只使用“必须 / 尽量 / 避免”三档，不出现权重数字。
2. **系统硬规则锁定。** 班级不撞课、教师不撞课、教室容量/类型、固定时间、教师不可用时间、锁定课程由系统保证，不做开关。
3. **用户配置的是学校政策。** 用规则库表达学科上限、时间偏好、教师负荷、半天无课等。
4. **先做 8~12 条高频规则。** 覆盖大多数中小学场景，不追求大而全。
5. **规则必须可解释。** 创建时显示影响范围，排课前提示冲突，排课后解释未排原因。
6. **渐进式披露。** 常用规则 → 高级规则 → 专家导入，三层能力，不用一套界面服务所有人。
7. **规则定义数据化、组件化。** 规则类型、参数、文案、校验、求解器映射集中管理，不在 JSX 里堆条件。

一句话：

> 把“约束设置”改造成“学校政策编辑器 + 影响预览 + 结果解释”，而不是继续加滑块。

- 教师不可用时间改为下拉添加、标签移除。
- 排课规则改为中文规则卡片，移除了技术权重滑块。

这些改动解决了“反复跳转”和“看不懂”的第一层问题。

### 1.2 仍然存在的核心差距

| 维度 | 当前状态 | 问题 |
|---|---|---|
| 规则表达 | 只读规则卡片 | 用户能看懂，但无法表达自己学校的政策 |
| 规则类型 | 班级/教师冲突、教室容量/类型、固定时间、教师不可用 | 缺少学科上限、时间偏好、教师负荷、连堂等 |
| 优先级 | 只有系统硬约束 | 没有“必须/尽量/避免”的用户语言 |
| 规则作用域 | 全局 | 不能按年级、班级、教师、学科设置 |
| 冲突反馈 | 通用 preflight 提示 | 不能指出是哪几条规则冲突 |
| 未排解释 | 总体说明 | 不能解释某个班/某位教师为什么排不进去 |
| 调整方式 | 整张重新排课 | 已支持规则模拟放宽；局部修复仍缺 |
| 结构约束 | 只有固定时间 | 没有连堂、合班、走班、选修、多周 |
| 规则治理 | 无 | 不知道规则谁改的、为什么改、影响谁 |
| 维护方式 | main.tsx 很大 | 继续加规则会难以维护 |

核心判断：

> 当前问题不是“规则太少”或“规则太多”，而是缺少一个可理解、可解释、可维护的规则产品模型。

## 2. 市场观察：成熟软件怎么做，痛点在哪

> 以下是产品层面的共性观察，不同厂商、版本和部署方式会有差异。

### 2.1 用户表达约束的常见方式

1. **直接标时间**：教师某天不可用、某节课不排、固定时间。
2. **规则清单/勾选**：必须、尽量、避免；按教师/班级/学科/教室设置。
3. **模板/预设**：小学低年级上午主科、体育不排第一节、教师半天无课。
4. **权重/优先级**：高级用户调节约束强度。
5. **Excel/表格导入**：教师不可用时间、教学计划、教室资源。
6. **自然语言**：新兴产品开始支持“数学每天不超过两节，尽量上午”，但通常需要确认解析结果。

### 2.2 成熟软件的典型解法

| 类型 | 代表产品 | 典型做法 |
|---|---|---|
| K12 商用 | aSc Timetables、Untis、TimeTabler | 规则库 + 硬/软约束 + 权重 + 自动排课 + 手动锁定 + 报告 |
| 开源/技术型 | FET | 硬约束/软约束分类细，约束类型多，界面偏工程化 |
| 轻量型 | Prime Timetable | 规则相对简单，拖拽 + 冲突提示，适合中小学校 |
| 国内教务 | 正方、强智、青果等 | 排课条件勾选、优先级、预排/正排、人工调整，流程贴合国内教务 |
| 大学排课 | Infosilem、Syllabus Plus | 政策驱动、学生分组、课程模块、资源统一建模，实施重 |

共性能力：

- 主数据和约束分开管理。
- 自动排课 + 手动调整 + 锁定。
- 硬约束保证可行，软约束负责“尽量好看”。
- 权重/优先级给高级用户。
- 冲突提示和报告。
- 部分产品支持代课、调课、版本。

### 2.3 成熟软件仍然存在的痛点

1. **硬/软语义错位。** 用户说“最好”“尽量不要”，系统要求权重数字。
2. **权重是黑盒。** 调一个数字，可能让另一门课变差，用户无法预测。
3. **冲突不可解释。** 只告诉用户“无解”或“有课未排”，不告诉是哪条规则导致。
4. **复杂度悬崖。** 简单界面表达不了合班/走班/连堂；专家界面又太难。
5. **例外难处理。** 教师请假、考试周、临时调课，往往只能整张重排。
6. **规则没有治理。** 规则越积越多，没人知道来源和影响。
7. **数据与规则分散。** 教师时间在 Excel，计划在教务系统，规则在排课软件。
8. **协作弱。** 教务主任、年级组长、排课老师之间缺少版本和审批。
9. **结果质量不可预期。** 可行不等于教学上合理，权重调不出“学校想要的样子”。

这些痛点说明：

> 成熟软件的护城河不只是求解器，而是“约束库 + 实施经验 + 可解释的调整流程”。  
> 但它们的弱点也很明显：复杂、黑盒、难治理。

## 3. 产品定位与原则

不做“什么都能配”的大型教务系统，先做：

> 中小学场景下，最容易看懂、最容易解释、最容易局部修改的排课工具。

### 3.1 约束是学校政策，不是求解器参数

用户界面出现的关键词应该是：必须、尽量、避免、作用范围、影响。

而不是：hard constraint、soft weight、penalty、迭代次数。

### 3.2 默认简单，高级可扩展

1. **常用规则**：8~12 条，勾选/参数化，覆盖大多数学校。
2. **高级规则**：用句子构建器添加，支持作用域、时间、例外。
3. **专家模式**：导入/导出规则 JSON，供实施人员使用。

### 3.3 硬规则锁定，偏好可配

系统保证的规则：

- 班级同一时间不撞课
- 教师同一时间不撞课
- 教室容量/类型匹配
- 固定时间生效
- 教师不可用时间生效
- 锁定课程保留

这些不做开关。用户可配置的是政策偏好，例如：

- 数学每天不超过 2 节（尽量）
- 体育不排第一节（避免）
- 语文尽量上午（尽量）
- 教师每周半天无课（尽量）

### 3.4 解释优先于配置

每个规则、每次排课都要回答：

1. 这条规则影响谁？
2. 它和别的规则冲突吗？
3. 某节课为什么没排进去？

### 4.3 规则创建：句子构建器

~~~text
对象     [教师 张老师 v]
时间     [每周三 下午 v]
限制     [不排课 v]
程度     [必须 v]

预览：张老师每周三下午不排课

影响：3 个班级 / 8 节课
[取消] [保存规则]
~~~

支持的句子模板：

- 某教师 某时间 不排课
- 某学科 每天 最多 N 节
- 某学科 尽量 上午/下午
- 某教师 每周 至少 N 个半天无课
- 某班级 每天 最多 N 节
- 某课程 连续 2 节
- 某教室类型 优先/仅允许

### 4.4 未排原因

~~~text
未排 2 节

七年级1班 · 数学 · 还缺 2 节
可能原因：
· 张老师周三下午不可用（必须规则）
· 可用数学教室不足（容量/类型）
建议：
· 释放周三下午可多排 2 节
· 增加 1 间数学教室

[模拟调整] [去修改教师时间]
~~~

要求：

- 明确写“可能原因”，不伪造数学证明。
- 每个建议能点到对应数据/规则。
- 不承诺最优解；启发式求解器只能给“预计/可能”。

### 4.5 影响预览

新建/编辑规则时先计算：

- 影响班级数
- 影响教师数
- 影响课时数
- 与现有规则的冲突
- 是否需要重新排课

不要保存后才告诉用户“这条规则会导致无解”。

## 5. 规则模型

### 5.1 用户语言与内部含义

| 用户语言 | 内部含义 | 求解器处理 |
|---|---|---|
| 必须 | 硬约束 | 必须满足；不满足则不可行 |
| 尽量 | 软约束，正向偏好 | 加分/减 penalty，允许违反 |
| 避免 | 软约束，负向偏好 | 减分/加 penalty，允许违反 |
| 系统保证 | 不可关闭的硬约束 | 固定逻辑，不进入用户权重 |

默认界面不出现数字权重。

### 5.2 规则结构

每条规则包含：作用对象、作用时间、限制内容、重要程度、例外、说明、启用状态。

示意 TypeScript：

~~~ts
type Importance = 'must' | 'prefer' | 'avoid';

type RuleScope =
  | { type: 'all' }
  | { type: 'grade'; grade: string }
  | { type: 'class'; classId: string }
  | { type: 'teacher'; teacherId: string }
  | { type: 'subject'; subjectId: string }
  | { type: 'room'; roomId: string };

type RuleTime =
  | { type: 'all' }
  | { type: 'weekday'; days: number[] }
  | { type: 'periodRange'; days?: number[]; from: number; to: number }
  | { type: 'term'; from?: string; to?: string };

interface RuleInstance {
  id: string;
  kind: RuleKind;
  scope: RuleScope;
  time: RuleTime;
  importance: Importance;
  params: Record<string, unknown>;
  enabled: boolean;
  note?: string;
  createdAt: string;
  source: 'preset' | 'manual' | 'import' | 'migration';
}
~~~

### 5.3 规则清单（P0 建议）

| 类别 | 规则 | 默认程度 | 说明 |
|---|---|---|---|
| 教师 | 教师不可用时间 | 必须 | 已有，保留 |
| 教师 | 教师每日最多 N 节 | 尽量 | 防止过载 |
| 教师 | 教师连续上课最多 N 节 | 尽量 | 减少疲劳 |
| 教师 | 教师每周至少 N 个半天无课 | 尽量 | 教研/备课 |
| 课程 | 学科每天最多 N 节 | 尽量 | 防止同一学科扎堆 |
| 课程 | 学科尽量上午/下午 | 尽量 | 语数英常见偏好 |
| 课程 | 学科避免第一节/最后一节 | 避免 | 体育/活动课常见 |
| 课程 | 学科分散到一周 | 尽量 | 避免一天集中 |
| 教室 | 教室类型匹配 | 必须 | 已有 |
| 教室 | 教室容量满足班级 | 必须 | 已有 |
| 结构 | 固定时间 | 必须 | 已有 |
| 结构 | 连堂/双节 | 必须 | 新增，先支持简单两节连排 |

P1 再增加：合班课、走班/选修、多周/单双周、教室设备/功能室、教师偏好时间段。

### 5.4 规则注册表

不要为每条规则写一套独立 JSX。使用“规则定义 + 实例”模式：

~~~ts
interface RuleDefinition<P> {
  kind: RuleKind;
  category: 'teacher' | 'subject' | 'room' | 'structure';
  title: string;
  description: string;
  importanceOptions: Importance[];
  scopeTypes: RuleScope['type'][];
  timeModes: RuleTime['type'][];
  defaultParams: P;
  paramFields: ParamField[];
  validate(rule: RuleInstance): string[];
  impact(rule: RuleInstance, data: SchoolData): RuleImpact;
  toSolver(rule: RuleInstance): SolverRule;
  explain(rule: RuleInstance): string;
}
~~~

好处：

- 新增规则只加一个定义，不改页面结构。
- UI、校验、求解器映射、说明文案共用一份定义。
- 测试可以按规则类型参数化。
- 以后做导入/导出、规则市场、预设都容易。

## 6. UI 可读性规范

“一眼看懂”不是把字放大，而是让用户在每个区域只回答一个问题。

### 6.1 规则卡片

统一结构：

~~~text
标题：数学每天不超过 2 节
范围：初中部 · 数学
时间：每天
程度：尽量
影响：12 个班 / 48 课时
操作：编辑 / 停用
~~~

要求：

- 标题用完整句子，不用内部 ID。
- 范围、时间、程度三行固定位置。
- 影响用“班级/课时”而不是“变量数”。
- 状态使用“文字 + 图标 + 颜色”，不只靠颜色。
- 一张卡只放一个规则。

### 6.2 视觉层级

- 页面标题 24~28px
- 区块标题 16~20px
- 卡片标题 14~16px
- 正文 12~13px
- 辅助说明 11~12px
- 行高不低于 1.45
- 正文最大宽度约 720px
- 规则用卡片，数据用表格

### 6.3 状态与颜色

- 绿色：通过 / 已启用 / 已保存
- 琥珀：待处理 / 有偏好冲突 / 需要确认
- 红色：不可行 / 硬冲突 / 保存失败
- 灰色：停用 / 不适用

每个状态必须有文字，例如“有冲突”，不能只有红点。

### 6.4 操作

- 每个区域只有一个主按钮。
- “新建规则”是主操作，“导入/导出”放次级菜单。
- 删除规则用二次确认，说明影响范围。
- 保存后不要跳页；保留当前滚动位置。
- 规则编辑用右侧抽屉，不覆盖整个页面。

### 6.5 空状态和错误状态

空状态必须给下一步：

- 还没有规则。先用推荐规则，或新建一条。
- 没有冲突。可以进入排课任务。

错误状态必须给可执行动作：

- 这条规则与“实验室连堂”冲突。查看冲突 / 调整时间 / 停用一条。

### 6.6 渐进披露

- 默认显示常用规则和系统保证。
- 高级选项折叠，不默认展开。
- 参数超过 3 个的规则，用“更多设置”展开。
- 不把 JSON、权重、求解器术语放在一级界面。

packages/constraints/

  presets.ts      # 学校类型预设
  explain.ts      # 规则说明/影响文案
  solver.ts       # 到 SolverInput 的映射
~~~

原则：

- 页面只负责布局和交互，不写规则判断。
- 规则类型定义只有一份。
- 文案集中管理，避免同一句规则在三个地方写法不同。
- Solver 输入适配层独立，UI 不直接拼 JSON。

### 7.2 状态管理

- 规则列表、当前筛选、编辑草稿放在 useRules 或页面级 reducer。
- 不要把规则编辑状态堆进 App。
- 规则变更统一走 commit，保证候选课表失效和保存策略一致。
- 提供派生 selector：activeRules、ruleConflicts、ruleImpact，避免组件重复计算。

### 7.3 数据兼容

当前数据里已经有 unavailableSlots、教学计划的 fixedSlotId、旧的 softConstraints。

迁移策略：

1. 保留旧字段，保证已有工作区能打开。
2. 新增 rules: RuleInstance[] 作为新模型。
3. 首次加载时把 unavailableSlots、固定时间转换成系统规则/数据约束，不重复写。
4. 旧 softConstraints 不再展示；可映射为默认偏好或忽略，并在迁移日志说明。
5. Solver 输入增加 rules，旧字段继续传，保证 Java 端可以渐进升级。

### 7.4 求解器接口

建议新增：

~~~ts
interface SolverRule {
  id: string;
  kind: RuleKind;
  scope: RuleScope;
  time: RuleTime;
  importance: Importance;
  params: Record<string, unknown>;
}
~~~

Java 端先支持 P0 中最有价值的 4~6 类：

- 学科每日上限
- 学科时间偏好
- 教师每日上限
- 教师连续上限
- 教师空档/半天无课（可先做惩罚）
- 连堂（结构）

不能一次全支持时，UI 必须标记“当前求解器暂不支持”，不能让用户以为生效。

### 7.5 测试

- 规则定义：参数校验、默认值、作用域文案。
- 影响计算：给定数据，影响班级/课时数正确。
- 冲突检测：硬冲突、软冲突、无冲突。
- 迁移：旧工作区加载后规则数量正确，候选课表不被误清空。
- 组件：规则卡片、构建器、空状态、错误状态。
- 集成：创建规则 → 保存 → 排课 → 解释面板。
- 可访问性：键盘、焦点、ARIA、颜色对比。
- 固定数据集：tests/test_data 的 Excel 导入后跑规则链路。

## 8. 分阶段实施

### Phase 1：规则模型 + 8 条常用规则（P0）

目标：用户能表达最常见政策，且看得懂。

交付：

- packages/constraints 规则类型/注册表/校验。
- 排课规则页：规则列表、系统保证折叠、规则卡片。
- 规则构建器：对象/时间/限制/程度四段式。
- 8 条规则：教师每日上限、连续上限、半天无课、学科每日上限、上午偏好、避免第一节、分散、连堂。
- 每个规则显示影响数量。
- 保存前冲突检查。
- 排课任务页“未排原因”基础版。
- 旧工作区迁移。

验收：

- 新用户不看文档，2 分钟内能创建“数学每天不超过 2 节”。
- 规则卡片不出现权重数字。
- 硬冲突能指出具体规则。
- 未排课程能显示至少一条可能原因。
- 组件拆分后 main.tsx 不再新增规则逻辑。

### Phase 2：解释与模拟（P1）

- 规则冲突最小集合（近似即可，明确“可能”）。
- 未排原因 + 建议释放哪条规则。
- What-if 模拟：放宽一条规则，预计多排几节（基础版已实现）。
- 自然语言输入 + 解析确认。
- 学校类型预设：小学/初中/高中。
- 规则例外：考试周、临时日期。
- 教室设备/功能室。
- 规则导入/导出。

### Phase 3：结构约束与协作（P2）

- 合班课、走班、选修。
- 多周/单双周。
- 场景对比（方案 A/B）。
- 规则版本、审批、审计。
- 局域网多人协作和权限。
- 增量修复：锁定后只重排受影响范围。
- 更大规模求解性能。

## 9. 成功指标

产品指标：

- 新用户完成第一条规则的时间 < 2 分钟。
- 80% 的规则来自预设或 8 条常用规则。
- 规则创建后，用户能正确说出它的影响范围。
- 排课失败时，用户能找到至少一条可操作原因。
- 规则相关支持问题下降。

技术指标：

- 规则新增不需要修改页面布局。
- 单条规则从定义到 UI + solver 映射 < 1 个文件改动（注册表驱动）。
- 规则校验/影响/解释有单元测试。
- 旧工作区迁移成功率 100%。
- 规则数量增长时页面性能稳定（100 条规则以内）。

## 10. 风险与开放问题

### 风险

1. **求解器暂时不支持所有规则。** 必须标记“暂未生效”，不能假装支持。
2. **解释不等于证明。** 启发式求解器给的是可能原因，文案避免“数学证明”口吻。
3. **规则过多导致不可行。** 必须提供冲突检测和“必须/尽量”降级建议。
4. **自然语言误解析。** 必须显示结构化预览，用户确认后才保存。
5. **UI 再次膨胀。** 用规则注册表和渐进披露约束，不回到滑块面板。

### 开放问题

- 首批 8 条规则是否覆盖目标学校？需要 3~5 位教务老师验证。
- 目标学段是小学、初中还是高中？首批预设不同。
- 是否需要支持单双周作为 P1 而不是 P3？
- 未排原因做到“启发式建议”还是只做“规则命中列表”？
- 规则变更后是否强制重新排课，还是允许保留旧课表并标记过期？

---

## 11. 非目标

- 大学级排课（学生分组、课程模块、跨校区）。
- 完整的最优性证明。
- 无确认的自然语言自动改规则。
- 把所有权重/求解器参数暴露到默认界面。
- 一次性覆盖所有合班/走班/选修场景。

## 12. 结论

排课软件的用户不是不会配置，而是：

- 不想学求解器术语；
- 不想面对一堆互相影响的数字；
- 不想在排不出来时只能猜；
- 不想改一条规则就推翻整张课表。

所以下一步的重点不是“加更多约束开关”，而是：

> 规则库 + 三档语义 + 影响预览 + 未排解释 + 局部修复。

这份方案先做小、做实、可解释，再逐步扩展结构约束。  
先把 8 条高频规则做对，比做 50 条没人看得懂的规则更有价值。
