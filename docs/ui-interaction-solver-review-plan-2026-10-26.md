# WarpWeft Scheduler UI、交互与求解缺陷审查计划

> 日期：2026-10-26  
> 状态：实施中；2026-10-26 已完成第一批 P0 修复及第二批 P0/P1 交互收敛，剩余 P1/P2 按阶段继续
> 范围：当前仓库 `D:\Projects\vibecoding\WarpWeft-Scheduler` 的桌面/网页 UI、排课准备与排课任务流程、规则配置、课表调整和 Java 启发式求解器。

## 1. 审查结论

当前产品已经形成“排课准备 → 规则 → 排课任务 → 检测/预览 → 调代课/发布”的主流程，固定时间、单双周、连堂、局部重排、长时任务和未排原因等能力也已有实现。但现在的主要缺陷不是功能数量不足，而是三个层面之间仍有断点：

1. **用户看到了很多状态，却不总能判断下一步该做什么。** 页面信息密度高，导入、排课、检测、调整都把大量说明和操作堆在同一层；失败时虽然有提示，但缺少“先改哪一项”的行动路径。
2. **规则产品语言与求解器真实语义没有完全统一。** UI 同时暴露“必须/尽量/避免”和 0–5 数字权重；部分规则是硬约束、部分是软目标、部分只是预检或启发式提示，用户很难建立稳定预期。
3. **求解结果缺少可比较、可追溯、可证明边界。** 当前求解器是启发式搜索，能返回可行候选，但未找到不等于数学无解，软分数也缺少“改善了什么、牺牲了什么”的对比；候选、调整和发布版本的差异链路仍不完整。

本计划原用于定义后续工作；2026-10-26 已开始执行第一批 P0 修复，下面的计划仍作为剩余工作的验收依据。

### 1.1 已实施的第一批修复（2026-10-26）

- 求解结果保留兼容的 `status=FAILED`，新增 `outcome`：`hard-conflict`、`partial`、`timeout`、`feasible`、`error`，避免把启发式未完成误报成数学无解。
- 排课任务页对部分候选和超时结果给出证据边界与“按当前配置重新计算”动作；阶段进度和长时任务进度明确标注为阶段/已排比例，不代表搜索完成度或最优性。
- Excel 导入改为解析校验后先展示变更预览，确认后才写入；工作区在预览期间发生变化时禁止覆盖。
- 规则与软偏好修改在存在候选课表时先提示候选会被清除；软偏好默认显示语义档位，高级设置才显示 0–5 权重。

### 1.2 已实施的第二批 P0/P1 修复（2026-10-26）

- 最终课表增加候选版与正式版差异入口：按课时列出新增、移除、时间/教师/教室/锁定状态变化，并同时显示软目标质量变化和当前人工调整记录数。
- 短时计算详情增加软目标分项：显示总质量、各项惩罚值和“质量越高/惩罚越低”的解释，避免只看一个不可解释的总分。
- 检测报告中的规则问题增加“去规则”直接动作，定位后可进入对应规则区继续修改和重算。
- 调代课页增加“撤销当天调整”，批量撤销会二次确认并写入独立审计记录，保留逐条撤销能力。
- 服务端暂时离线时增加显式“重新连接”动作，重试会重新执行健康检查、鉴权和工作区加载，不要求刷新页面。
- 运行模式设置增加目标服务端连接测试；启动健康检查对短暂服务重启自动重试一次，并显示 schema/Solver 协议版本。
- 排课向导补充模型边界说明：普通计划单教师、走班块多教师、简化/完整教室模式，以及配对单双周和连堂的支持范围。
- 课表预览中的移动、交换、锁定/解锁和撤销写入统一审计日志，便于追溯手动调整来源。
- 候选版和正式版写入持久化版本元数据（版本 ID、来源、父版本、摘要、调整数量）；规则/数据变更清除候选时同步清除候选版本指针。
- 大课表时限提示增加可直接采用的建议按钮，并明确时限只增加启发式尝试次数，不代表搜索完成度或最优性。
- 检测报告对未排课时和教师不可用问题增加“去调整”入口，规则问题继续提供“去规则”入口。
- 排课设置增加可编辑随机种子；短时记录保留实际种子，详情页可据此复现同一输入的启发式运行。
- 局部重排区域显示范围内可移动/锁定课时及范围外保持不变的课时数量，避免把局部修复误解为整表重排。

本批验证：新增 `timetableDiff` 单元测试通过；构建通过；调整、检测相关测试通过。完整全量测试仍需在本批提交前再跑一次。

当前 P 级行为修复已覆盖 P0/P1 的状态语义、导入与规则风险提示、候选/正式版追溯、检测责任入口、调代课撤销审计、连接恢复、软目标解释、模型边界、时限建议、随机种子复现和局部重排范围摘要。剩余工作集中在 Phase 5 的截图/设备回归、真实大规模求解耗时采样，以及 P2 的凭据治理等验证或规划项。

## 2. 证据与现状问题

### 2.1 UI 视觉与信息架构

| 优先级 | 问题 | 现象/证据 | 影响 |
|---|---|---|---|
| P0 | 排课失败后的主行动不够明确 | `RunsPage.tsx`、`runViews.tsx` 同时展示预检、计算设置、短时历史、长时任务、未排原因；用户需要自己判断是改数据、改规则、局部修复还是继续计算 | 失败后容易反复点击“重新排课”，无法形成闭环 |
| P0 | 导入抽屉缺少“文件 → 预览 → 差异 → 确认”的中间态 | `ResourcesPage.tsx` 的导入界面在未选文件时占据整侧抽屉，主要是说明文字；当前截图 `build/shots/import-panel-new.png` 显示大量空白，且导入前看不到将新增/更新/冲突/跳过什么 | 高风险操作缺少可逆确认，用户容易整库覆盖或误导入 |
| P1 | 规则页面同时使用自然语言档位和数字权重 | `RulesPage.tsx` 使用“必须/尽量/避免”，`SoftConstraintPanel.tsx` 又显示 0–5 权重，并说明权重不保证目标为 0 | 用户无法预测“必须”和软权重之间的优先关系；调参成本高 |
| P1 | 页面层级与视觉层级不一致 | 截图中的侧栏、顶部运行状态、卡片、英文 kicker、长说明同时争夺注意力；`style.css` 规则/任务/检测页面大量使用窄字号和多层卡片 | 首次使用者难以找到核心动作，长页面滚动成本高 |
| P1 | 检测结果信息量大，但缺少按责任归因的修复路径 | `InspectionPage.tsx` 能列出硬冲突、必需规则、未排课时和资源利用率；截图 `build/shots/inspection-bad2.png` 显示问题项可定位，但定位后主要回到表格，缺少“修改规则/释放资源/重排范围”的上下文动作 | 检测报告更像报表，不能直接驱动修复 |
| P1 | 调代课流程把“选择对象、影响范围、记录历史”放在同一长页面 | `AdjustmentsPage.tsx` 及截图 `build/shots/adjust-swap-1440.png` 同时显示日期、班级、课程列表、影响范围和撤销记录 | 操作人员在窄屏或低分辨率下容易迷失当前状态，撤销与新建的边界不够强 |
| P2 | 状态反馈分散在 toast、页内提示、历史记录和弹窗 | `toastLog.ts`、`main.tsx`、`ShortRunDialog.tsx` 分别保存和展示不同层级的结果 | 错误可能被短时 toast 掩盖，用户难以回看完整因果链 |
| P2 | 响应式策略主要是“堆叠/隐藏”，不是重排工作流 | `style.css` 在 680/820/1180px 处大量隐藏或压缩控件；窄屏时关键表格仍可能需要横向滚动 | 1024px 以下的排课准备和检测页面可用性下降 |

### 2.2 交互与数据安全

| 优先级 | 问题 | 现象/证据 | 影响 |
|---|---|---|---|
| P0 | 导入、规则修改、候选课表失效之间的关系不够可见 | 规则保存会 `invalidate` 当前候选；软约束修改也会清除候选，但页面只在局部说明 | 用户可能以为只是改了偏好，实际已经丢失当前候选结果 |
| P0 | 候选、正式版、调整叠加版之间缺少统一版本差异入口 | `single-machine-audit.md` 已将“候选课表和正式版增加版本差异查看”列为后续计划；当前调整模型独立叠加在周课表上 | 发布前无法快速回答“这次到底移动了哪些课、哪些是人工调整” |
| P1 | 手动调整的撤销边界和批量撤销不足 | `single-machine-audit.md` 明确列出操作日志和批量撤销仍待完善 | 误拖、误锁、误解锁后的恢复成本高 |
| P1 | 服务端/网络模式的连接失败恢复不完整 | `single-machine-audit.md` 记载客户端连接测试、错误码和自动重试仍待；`linux-server-parity.md` 也列有浏览器/桌面能力差异 | 用户把网络暂时失败误认为数据或求解失败 |
| P2 | 保存账号密码的风险提示存在，但治理能力弱 | `savedLogins.ts` 和登录界面支持本机保存未加密密码，依赖用户主动清理 | 共用电脑场景容易留下长期凭据；应改为会话令牌/系统凭据存储规划项 |

### 2.3 求解器与规则语义

| 优先级 | 问题 | 现象/证据 | 影响 |
|---|---|---|---|
| P0 | “未找到”与“无解”仍可能被用户混淆 | `server/fullsolver/README.md`、`server/fullsolver/Main.java` 明确标注启发式 oracle、`proof: false`；`runViews.tsx` 也写明未排原因不是数学证明 | 错误的硬冲突判断会导致用户错误放宽规则或修改有效数据 |
| P0 | 规则冲突分析是近似检测，不是最小不可行集证明 | `RulesPage.tsx` 明示“近似检测”；FullSolver 通过反复调用启发式求解器判断子集 | 规则页的冲突数量和求解器最终失败原因可能不一致 |
| P1 | 软目标评分缺乏可解释的相对比较 | `SolverOutput.scoreBreakdown` 有分项分数，但 `ShortRunDialog.tsx` 主要展示总结果；没有候选 A/B、基线、权重变化带来的代价说明 | 用户看到“评分更高/更低”，却不知道对课表质量意味着什么 |
| P1 | 求解过程进度仍是阶段/检查点，不是真实完成百分比 | `docs/single-machine-audit.md` 明确指出阶段进度是客户端阶段状态；Java `Scheduler.publish` 输出已排/总数和 score，但搜索空间完成度不可知 | 进度条容易被理解为“还剩多少时间”或“接近最优” |
| P1 | 大规模满课表、硬锚点多时可能耗尽时限 | `docs/algorithm-model-upgrade-2026-10-25.md` 记载整校满格 + 大量硬锚点时 30 秒可能偏紧，仍是找到可行解而非最优性证明 | 同一份数据在不同随机种子/时限下结果稳定性不足 |
| P1 | 多教师、班级固定教室等模型边界尚未闭合 | `docs/algorithm-model-upgrade-2026-10-25.md` 的后续项列出协同教学/多教师、班级-教室绑定、配对+连堂组合 | UI 可能允许用户表达场景，但求解器只能退化、拒绝或用简化模型处理 |
| P2 | 局部重排的“保留范围”需要可验证报告 | `RunsPage.tsx` 支持按班级/教师/规则局部修复，求解器有 seed/locked 条目；当前结果展示没有统一列出“范围外保持不变”的证明式摘要 | 局部修复可能被误认为整表重新优化，人工锁定边界不清晰 |
| P2 | 随机种子和可复现性没有面向用户治理 | `main.tsx` 默认 `randomSeed: 1`，Java 内部多处 `shuffle` 和随机抖动；UI 没有结果复现/比较入口 | 同样配置的多次计算无法方便比较，问题复盘困难 |

## 3. 后续计划

### Phase 0：先统一产品语义与验收口径

1. 定义状态模型：`数据错误`、`规则冲突`、`求解中`、`找到可行解`、`未排满`、`超时未知`、`已发布`，每个状态明确允许的下一步。
2. 统一“必须/尽量/避免”和数字权重的关系：普通用户只看语义档位，高级诊断才显示权重与分项分数。
3. 统一结果文案：所有“无解”改为带证据等级的“未找到可行解/当前时限内未找到/检测到硬冲突”。
4. 为候选、正式版、调整叠加版定义版本 ID、来源、父版本、变更摘要和可回滚边界。

验收：产品文案、数据模型、UI 状态标签和 solver 输出字段使用同一套枚举；任何失败结果都能直接给出下一步动作。

### Phase 1：重做排课任务的失败闭环（P0）

1. 将排课任务改成“预检 → 选择策略 → 计算 → 结果决策”的单一工作流。
2. 结果顶部固定显示：已排/计划、未排、硬冲突、软分数、耗时、时限、随机种子、结果可信度。
3. 未排项按责任来源聚类：数据缺失、资源不足、规则命中、求解器未找到；每类提供查看对象、修改入口、局部重排或继续计算。
4. 对局部修复显示范围锁定摘要：范围内允许移动的课程数、范围外保持不变的课程数、锁定课程数。
5. 将短时历史、长时任务、当前候选分成“当前结果 / 历史记录 / 后台任务”三个明确区域。

验收：对一个未排样例，用户不阅读源码即可回答“缺了什么、改哪里、改后怎样重算”。

### Phase 2：导入与规则编辑的可逆交互（P0/P1）

1. 导入改为四步：选择文件、解析预览、差异与风险、确认写入；支持按工作表查看新增/更新/冲突/跳过。
2. 明确“清空当前工作区”是高风险操作，显示影响范围、数据备份入口和确认后的结果摘要。
3. 规则保存前显示候选课表失效提示，并提供“保存并清除候选 / 保存为草稿 / 取消”路径。
4. 规则页增加示例和影响预览：某规则命中多少班、多少课时、预计会挤压哪些资源；把 0–5 权重收进高级设置。
5. 规则冲突定位后提供直接动作：编辑规则、查看受影响计划、模拟放宽、复制为软规则。

验收：导入和规则修改均可在写入前预览；写入后能看到变更摘要；取消不会改变工作区。

### Phase 3：检测、课表预览和调整工作流收敛（P1）

1. 检测项增加“为什么、影响谁、建议动作、修复后重检”四列/四段信息。
2. 课表预览增加候选与正式版差异视图，支持按班级、教师、时间、锁定状态筛选。
3. 调代课拆成“选择日期/班级 → 选择课程 → 选择动作 → 预览影响 → 保存 → 撤销/审计”步骤；长页面只保留当前步骤所需内容。
4. 为拖动、锁定、解锁、调课、对调增加统一操作日志和批量撤销。
5. 发布前固定展示：候选版本来源、未解决问题、人工调整数量、与上一版差异、可回滚版本。

验收：一次手动调整可以追溯到操作者、原位置、目标位置、原因和撤销记录；发布前不存在隐藏的候选/调整混用。

### Phase 4：求解器可信度与可解释性（P0/P1）

1. 将 solver 状态拆为 `feasible`、`partial`、`timeout-unknown`、`hard-conflict`，禁止用单一 FAILED 覆盖不同原因。
2. 输出每个未排课时的候选槽位统计、阻塞资源、命中的硬规则/必须规则，以及“证据等级：检查/启发式/证明”。
3. 输出候选结果与上一最佳结果的差分：新增位置、移出位置、锁定保持、软目标增减。
4. 将真实搜索进度改成“已运行时间 + 当前最好结果 + 最近改进时间 + 检查点时间”，不把已排比例伪装成百分比进度。
5. 增加固定随机种子、重复运行比较和结果导出，支持复盘同一输入在不同时间限制下的稳定性。
6. 把求解器模型边界显式化：多教师/协同教学、班级固定教室、配对+连堂、复杂走班场景分别给出支持级别和阻断提示。
7. 评估可证明求解器或混合策略的接入边界；在未接入前，所有冲突分析继续标注 `proof=false`。

验收：用户能区分“数据硬冲突”“当前时限未找到”“启发式未判断”和“已找到可行解”；任何结果都能导出输入、配置、种子、版本和摘要。

### Phase 5：可用性和性能验证

1. 以 1280×800、1024×768、1366×768 三种常用窗口建立 UI 回归截图基线；覆盖浅色/深色、空数据、完整数据、失败结果、长任务运行中。
2. 以小规模、整校满课表、固定锚点密集、单双周配对、资源不足五类数据做端到端脚本。
3. 记录从导入到发布的关键耗时、交互错误率、重复计算次数和撤销成功率。
4. 对大数据集检查主线程阻塞、表格滚动、导入预览、长时任务轮询和结果弹窗的可访问性。

## 4. 暂不执行项
